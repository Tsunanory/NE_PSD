# Desktop and Windows Delivery Implementation Plan

> Routing: [model-routing.md](../../model-routing.md). Ponytail full applies to coding, design and code review.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every worker activates task-observer. The requested review layer checks ready images at runtime; development tasks use ordinary tests and evidence.

**Goal:** Deliver a local desktop workflow that qualifies a PSD and exact local model, processes assets through the frozen JobService, exposes review/recovery evidence, and installs and works offline on Windows 11 x64.

**Architecture:** Electron main owns native dialogs, local services, trusted paths and process lifecycle; a sandboxed React renderer receives a narrow typed preload API. D develops against deterministic fake JobService and setup fixtures while A, B and C independently implement their packages after the common foundation commit. A composes the live service adapters; Windows acceptance uses the packaged application, licensed Photoshop and qualified local inference.

**Tech Stack:** Strict TypeScript, Electron, React, Vite, Zod, Vitest, Playwright Electron tests and electron-builder. Runtime and dependency versions come from the foundation's exact lock; production includes a separate pinned Windows Node runtime and the pinned MCP dependency tree.

## File and service map

| Paths | Responsibility |
|---|---|
| `apps/desktop/src/main/` | Electron window policy, native dialogs, allowlisted IPC, local setup adapters, JobService attachment and packaged runtime resolution. |
| `apps/desktop/src/preload/` | Fixed typed `window.nePsd` bridge; no raw `ipcRenderer`, Node API or filesystem access. |
| `apps/desktop/src/renderer/setup/` | PSD/assets/output selection, exact selector and three-variant qualification, local model setup. |
| `apps/desktop/src/renderer/jobs/` | Snapshot-driven job progress, safe-boundary controls and immutable review evidence. |
| `apps/desktop/src/renderer/shared/` | Small shared form, status and error primitives, Russian product copy, accessible keyboard handling. |
| `tests/desktop/fakes/`, `tests/desktop/fixtures/` | Deterministic JobService/setup adapters and data; no live Photoshop or model invocation. |
| `packaging/` | Windows builder configuration, pinned resource manifest, native-module smoke checks, installer and real-host acceptance scripts. |
| `docs/desktop/` | Setup instructions, exact prerequisite/version records, test evidence, task review packets and A-facing handoff. |

`apps/desktop/src/main/services.ts` defines the D-owned composition boundary. A exposes `createJobService` and `createSetupService` from `@ne-psd/core`; D accepts their frozen interfaces and supplies fake implementations until integration. SetupService also exposes `proposeConfiguration({instruction,inspectionId,modelProfileId}, signal) -> ConfigurationProposal`. Add an instruction text input, submit it through the setup facade to the selected qualified model, display cited proposed fields/missing facts, and validate before live qualification. No renderer direct model calls. SetupService methods are `inspectTemplate(templatePath, signal) -> InspectionReport`, `qualifyTemplate({inspectionId, proposal, workingTemplatePath}, signal) -> TemplateProfile`, `inspectModelProfile(profile, signal) -> {available, errors}`, and `qualifyModelProfile(profile, signal) -> {qualified, evidencePaths, errors}`. Do not rename them or invent a model-profile return value. A owns live composition. D wraps these methods with strict IPC schemas and native operations `chooseTemplate`, `chooseAssetsDirectory`, `chooseOutputDirectory`, `saveCandidate`, `loadCandidate`, `readEvidence`, `openCommittedOutput` and `dispose`. Dialog operations return root IDs and display labels; main retains canonical paths. Template qualification receives a frozen ConfigurationProposal and a job-owned working path; it returns TemplateProfile only after B/A qualification succeeds. Model setup inspects and qualifies an already schema-valid selected ModelProfile; both availability and qualification must pass, with C's evidence present. Failures expose DomainError, never raw backend objects. Persist candidate and verified profile forms separately. Human visual review must use A/C's qualified evidence workflow; never invent a desktop-only approval that bypasses JobService.
